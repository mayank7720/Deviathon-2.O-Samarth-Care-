## What the AI actually does

`lib/grounded-reports.mjs` computes a dated evidence snapshot from the senior's recorded observations. The window is seven days by default. It excludes other seniors, future dates, impossible dates, empty rows and out-of-range measurements. Independent same-day submissions are merged; medication totals are counted once per day. Missing days remain missing. A first-30-day warm-up cannot supply a future-derived personal baseline.

The facts contain measured averages, ranges, logged-day counts, recorded doses, personal-reference differences, supported note cues and unconfirmed sensor reports. Each fact points to evidence aliases. The coordinator can inspect the aliases' dates and original record references locally. A snapshot is bounded by its saved evidence fingerprint; a later observation requires a new report. Report generation does not change the clinical priority score.

The optional LLM generates a structured report plan: it selects and orders existing fact IDs, chooses a warm opening/closing, and retains the required human follow-up. The server renders the selected verified statements in English or Hindi. Free-form model assertions, invented numbers, diagnosis text, unknown fact IDs, repeated highlights, omission of coverage, omission of immediate-review evidence and reduced follow-up urgency are rejected. This is labelled **LLM-guided evidence-locked weekly report**, rather than pretending arbitrary prose has been medically fact-checked.

Computed mode uses the same factual renderer without an LLM. A missing, disabled, unavailable or invalid model produces an explicitly labelled computed report; it never becomes a successful LLM result. Both modes create review drafts. A coordinator approves family delivery separately, and current family consent is still required.

## Privacy boundary

`providerReportFacts()` is an explicit whitelist. The provider receives dates, supported aggregate values, non-identifying cue names, anonymous evidence aliases and approved statement choices. It receives no name, senior ID, email, telephone number, raw call note, contact detail or original record identifier. Derived health aggregates remain sensitive; masking does not make them anonymous. Use synthetic showcase data unless a governed real-data workflow has been established.

The published workflow's settings were read back from the n8n API after publication: successful/error data saving is `none`, and manual/progress saving is `false`. The native model request uses `store:false`. Early historical imports had used instance defaults; those observations do not describe the current published settings. Use synthetic showcase data rather than real health records in workflow examples.

The inspected showcase UI offered **$2.00 remaining** and **GPT-5-MINI**; that observation is not a permanent balance or a successful inference result. This path uses the native OpenAI v2.3 Responses operation, managed credentials, `store:false`, a bounded output and no tools. Its public app URLs are fixed, with no `$vars` or provider API key dependency. Select the existing encrypted Crypto HMAC credential on both signing nodes. Import this alternative in place of the generic report workflow because both use the same webhook path.

Native output validation accepts the node's parsed JSON or JSON text only after a completed response with actual model/response IDs. It rejects refusals, incomplete responses, extra outputs and unsupported evidence. Actual model identity is sent in the existing signed callback; the response ID remains in the node output and the app retains its n8n execution reference. Application evidence checks remain authoritative: current upstream node code exposes a strict option but omits that flag from the provider request builder. The separate live acceptance above establishes one executed report; importing the file alone establishes none.

Rebuild exports with `node n8n/build-workflows.mjs`, then import the JSON through n8n's **Import from File** action:

Assign these credentials after import:

- **Report model HTTP authentication**: the checked-in HTTP model template requires an HTTP Header Auth credential for the chosen inference endpoint. The header name/value depend on that provider. Secrets do not belong in the model URL or project variables. This HTTP template does not automatically use n8n Gateway credits; see the credits section below.

| Name | Meaning |
| --- | --- |
| `SAMARTH_APP_ORIGIN` | The deployed application's HTTPS origin, without a trailing slash |
| `SAMARTH_LLM_CHAT_URL` | The configured provider's complete chat endpoint; never copied from a webhook payload |

## Application contract

Server configuration uses `SAMARTH_N8N_ENABLED=true`, `SAMARTH_N8N_REPORT_WEBHOOK_URL` and the private signing secret. The webhook must be a published HTTPS `/webhook/` endpoint on an `n8n.cloud` subdomain or the configured `SAMARTH_N8N_ALLOWED_HOST`. Test endpoints and loopback HTTP require explicit development flags. Redirects are disabled.

The signature is HMAC-SHA256 in hex over the exact UTF-8 string `timestamp + "\n" + nonce + "\n" + rawBody`. Headers are `x-samarth-timestamp`, `x-samarth-nonce` and `x-samarth-signature`. Requests expire after five minutes. `verifyN8nEnvelope()` requires a durable insert-once nonce claim; a process-local set is not an acceptable deployed replay store.

The webhook's raw-body option is required. `Prepare ingress` reads those bytes with n8n's asynchronous `this.helpers.getBinaryDataBuffer(0, 'data')`, including storage-backed Cloud binary data. It never interprets a binary storage reference as Base64 or reserializes parsed request JSON before verifying the signature.

The report workflow claims `/api/integrations/n8n/claim` using the original signed envelope. A service-only database function locks the saved report job and changes `awaiting_n8n` to `claimed` exactly once. A fresh signed nonce cannot claim the same job again. The server responds only with its saved masked facts and schema. The workflow checks that response and immediately returns HTTP 202 with `status:processing` and `generationCompleted:false`; its connected output then continues to the model. The HTTP response does not contain a completed report. This avoids holding the application request open throughout model inference and callback storage.

The callback posts `/api/integrations/n8n/callback` with `{version:1, kind:"weekly_report.completed", jobId, factsHash, plan, model}` and a fresh signed nonce. The server requires a claimed job, checks its language, expiry and evidence fingerprint, independently validates the plan, and atomically creates a `pending_review` report. Client callbacks cannot approve a report. Unknown, unclaimed, expired, completed, tampered or replayed jobs fail closed. The report list shows claimed jobs as processing, keeps polling, and replaces them only when the stored report exists.

If submission times out or a workflow crashes, the saved job is retained. Repeating the same application request returns that saved state without sending another webhook. Inspect the actual execution before deliberately creating a new report request; never enable automatic retries of the model path. A failed model or callback does not create report text. An unfinished job is marked expired by the report reader after its 24-hour deadline; there is no automatic failure recovery or redial. HTTP acceptance, report generation, coordinator approval and family delivery remain separate states.

The phone workflow accepts exactly `{version:1, kind:"voice_checkin.request", jobId, language}`. The app resolves the saved destination and checks consent, authorized test numbers, configured transport and spending limits. Phone numbers and direct senior IDs are not passed through n8n. Real carrier delivery requires an enabled provider/credit allowance or suitable user-owned hardware; n8n orchestration alone does not supply telephone service. Provider acceptance, answered calls, delivered SMS and human read receipts are separate statuses.

## The 10,000-execution budget

The reported allowance counts workflow executions, rather than servers, node steps or seniors. The report webhook starts one execution for each explicitly requested senior report from the public or configured local application. Automatic weekly cohort-wide LLM batches are not enabled. The optional voice webhook would start another execution per dispatch request; the current website calls its protected trial-provider worker directly.

These are planning calculations, not a demonstrated capacity benchmark:

| Workload | Approximate monthly executions | Fit within the reported 10,000 allowance? |
| --- | ---: | --- |
| 200 seniors, one weekly report each (`200 × 52 ÷ 12`) | 867 | Leaves room for a limited showcase workload |
| 200 seniors, one daily report each, 30-day month | 6,000 | Leaves about 4,000 for other top-level runs |
| 10,000 seniors, one weekly report each (`10,000 × 52 ÷ 12`) | 43,333 | Exceeds the allowance before calls or other workflows |
| 10,000 seniors, one daily report each, 30-day month | 300,000 | Exceeds the allowance |

Keep routine vitals ingestion, rule/anomaly scoring and routine data storage in the application/Supabase job path. They do not require an n8n execution per measurement. For the showcase, request weekly LLM reports only for selected consented synthetic cases and keep an execution reserve for diagnosis-free communication tests. Monitor the actual usage meter; don't assume all runs are free or that retries consume nothing.

For a future 10,000-senior rollout, an administrator-controlled scheduled parent workflow could fetch a bounded page of due opaque jobs and process them in batches, preserving each senior's separate claim, evidence hash, callback and consent boundary. Node/item processing inside one workflow is not billed as one execution per step. This batch scheduler is a proposed expansion, **not implemented by these single-report webhook exports**. Batching does not remove model-token charges, carrier costs, concurrency limits, deadlines or memory bounds. Benchmark it and inspect the actual plan limits before making affordability or throughput claims.

## AI credits and zero additional spend

There are three separate balances or entitlements to check:

- **Workflow executions:** the reported 10,000 monthly Pro allowance runs automations.
- **Assistant credits:** n8n's workflow-building assistant has its own allowance.
- **Gateway credits:** current official documentation lists these for n8n Cloud Starter/Pro from n8n 2.36.0. Supported native model/service nodes can use the instance's prepaid balance without a provider API key. Availability, eligible models, supported operations and remaining balance must be inspected in this hackathon workspace. No balance amount is assumed here.

The inspected workspace offers **Gateway credits** on the native model node, and the Gateway export has passed one actual masked synthetic report. The original generic HTTP export still requires its own provider credential and cannot redeem those credits automatically. Use the matching export and retain its schema, validation and signed callback nodes. Another instance's eligible models, operations and balance must be checked separately.

For zero additional spend, use only an already-included balance, leave automatic top-ups off, and stop model runs when that balance is exhausted. The evidence-computed report remains available with its explicit no-LLM label. A local model is another option when suitable hardware is available; n8n Cloud cannot reach a laptop's loopback address directly. Neither a 10,000-execution allowance nor Assistant credits establish working phone service or included SMS/minutes. The existing SIM plan and prepared phone bridge have their own consent, hardware and carrier limits.
